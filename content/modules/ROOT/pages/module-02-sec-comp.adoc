= セキュリティとコンプライアンス

== はじめに

Mega-Saleは成功しましたが、重要なセキュリティ監査が迫っています。すべての仮想化ワークロードにおいて、業界のコンプライアンス標準を厳格に遵守していることを証明する必要があります。私たちの課題は、VMとコンテナの両方において、セキュリティに対する統一されたアプローチを確保することです。このモジュールでは、OpenShift Compliance Operatorを使用してインフラストラクチャをスキャンし、報告された脆弱性を修正することで、クラスターが厳格なセキュリティ標準を満たしていることを確認します。また、セキュリティ監査担当者が仮想化インフラストラクチャへのアクセスを制限する必要がある場合、専用のユーザーアカウントとアクセスロールを設定します。

[[scan_comp]]
== OpenShift Compliance Operator を使用したインフラストラクチャのスキャン

このラボのセクションでは、OpenShift Compliance Operator を使用して OpenShift クラスターのセキュリティスキャンを設定する方法に焦点を当てます。Compliance Operator は、OpenShift 環境内のホストが特定のセキュリティ標準に準拠していること、そしてそれらの標準に準拠するようにデプロイされていることを確認するのに役立ちます。

NOTE: ラボ環境では仮想ホスト環境であるため、ワーカーノードのスキャンと修復のみを行います。コントロール プレーンでこれを行うと、クラスターが不安定になる場合があります。

[[node_remediate]]
== OpenShift Compliance Operator を使用したノードの修復
修復には、2つの方法があります。自動修復はシンプルで最も簡単な方法のように見えますが、予期しない結果につながる可能性があります。手動修復は手間がかかりますが、各アプリケーションでカナリアテストを実施し、その後、処理を進める前に障害をチェックする gitops などのツールを使って自動化することができます。

NOTE: 一例として、*rhcos4-moderate-worker-enable-fips-mode* が挙げられます。これは前回のスキャンで重大度「高」、ステータス「失敗」と表示されており、インストール時に FIPS モードが有効になっていない限り適用できません。これを自動修復しようとすると、クラスターに問題が発生する可能性があります。

このセクションでは、前回のスキャンから失敗の 1 つを選択し、手動で修復します。

. 上記のリストから、監査の要件に従って、次のスキャン結果 *rhcos4-moderate-worker-coreos-pti-kernel-arguments* を修復することを選択します。
+
Note: https://bugzilla.redhat.com/show_bug.cgi?id=1519781[Meltdown^] 脆弱性のような攻撃を防ぐために、カーネルとユーザー空間のページ テーブルを分離するには、*rhcos4-moderate-worker-coreos-pti-kernel-argument* が必要です。
+
*Compliance Remediation* タブをクリックし、*Name* 検索バーに
`pti-kernel` と入力して、*rhcos4-moderate-worker-coreos-pti-kernel-argument* の推奨修復方法を検索します。結果が表示されたら、右側の3点メニューをクリックし、表示されるメニューから *Edit ComplianceRemediation* を選択します。
+
image::module-02-sec-comp/14-compliance_remediation.png[title="Compliance Remediation", link=self, window=blank, width=100%]
+
. これにより、現在のステータスを示すYAMLブロックを含むComplianceRemediationの詳細ページが起動します。
. *spec* セクションでは、現在の *apply* 状態が *false* であり、適用される *kernelArugument* が *pti=on* であることがわかります。*status* セクションでは、修復状態が *NotApplied* であることがわかります。
+
image::module-02-sec-comp/15-compred_details.png[title="Compliance Remediation Details", link=self, window=blank, width=100%]
+
. *spec* セクションで、*apply* フィールドを `true` に変更し、*Save* ボタンをクリックします。
+
image::module-02-sec-comp/16-compred_true.png[title="Compliance Remediation True", link=self, window=blank, width=100%]
+
. これが管理対象リソースであることを知らせるメッセージが表示されます。*Save* ボタンをクリックして修復プロセスを開始します。
+
image::module-02-sec-comp/17-managed_resource.png[title="Managed Resource Prompt", link=self, window=blank, width=100%]
+
. 適用すると、修復を提供するための *MachineConfig* が生成され、クラスター内の各ノードが順番に遮断、ドレイン、修復されます。
. 左側のメニューで、*Compute* と *Nodes* をクリックしてプロセスを確認します。
+
image::module-02-sec-comp/18-nodes_cordoned.png[title="Node 3 Cordoned", link=self, window=blank, width=100%]
+
. ノードが修復を開始するために _SchedulingDisabled_ 状態に移行しているのが確認できます。そのノードをクリックしてノードの詳細ページを表示すると、イベントログにノードが更新を適用するために停止されたことが示され、ノードのドレインが正常に完了したため、CPUとメモリの使用率が低下していることも確認できます。
+
image::module-02-sec-comp/19-node_3_updating.png[title="Node 3 Updating", link=self, window=blank, width=100%]
+
NOTE: このプロセスは、クラスターの現在の負荷状況や、修正対象のノード数に応じて、完了までにかなりの時間がかかる場合があります。これは、各ノードがポッドを安全に退避させ、再起動して更新を適用する必要があるためです。また、OAuthポッドの退避中は、クラスターからログアウトされている場合があります。
+
. 数分後、*MachineConfig* がクラスター内の各ワーカーノードに適用され、コンプライアンススキャンの結果を再確認できます。
. 左側のメニューで *Operators* と *Installed Operators* をクリックして、*Compliance Operator* 構成に戻ります。
+
image::module-02-sec-comp/02-compliance_operator.png[title="OpenShift Compliance Operator", link=self, window=blank, width=100%]
+
. Compliance Scan タブをクリックすると、先ほど完了したスキャンが表示されます。3点メニューをクリックし、現在のスキャンを削除するオプションを選択します。
+
image::module-02-sec-comp/20-delete_compliance_scan.png[title="Delete Compliance Scan", link=self, window=blank, width=100%]
+
. 現在のコンプライアンススキャンを削除するかどうかを確認するメッセージが表示されます。*Delete* ボタンをクリックしてください。
+
image::module-02-sec-comp/21-delete_scan_prompt.png[title="Delete Scan Prompt", link=self, window=blank, width=100%]
+
. 先ほど定義した *Compliance Suite* オブジェクトは自動的に新しいスキャンを開始し、画面に表示されます。
+
image::module-02-sec-comp/22-new_compliance_scan.png[title="New Compliance Scan", link=self, window=blank, width=100%]
+
. 以前と同様に、完了するまでに数分かかる場合がありますが、完了したら、*ComplianceCheckResult* タブをクリックし、 *rhcos4-moderate-worker-coreos-pti-kernel-argument* を検索して結果を表示できます。ラベルが *FAIL* ではなく *check-status=PASS* になっていることがわかります。

+
image::module-02-sec-comp/23-check_status_pass.png[title="Check Status Pass", link=self, window=blank, width=100%]

これらのセクションを完了すると、コンプライアンス スキャンが作成され、OpenShift Compliance Operator を使用して特定された脆弱性が正常に修復されました。

== Cクラスターロールに対するロールベースアクセス制御の設定

OpenShift が標準の Kubernetes と比較して特に優れている点の一つは、ユーザーアカウントとクラスターロールを個別に管理できる豊富なロールベースアクセス制御です。これらのロールベースアクセス制御により、クラスターにログインした各ユーザーが実行できる操作を定義できます。このモジュールのこのセクションでは、監査担当者用の読み取り専用アカウントを作成し、そのアカウントに適用される制限事項について説明します。

. まず、左側のメニューで *User Management* と *Users* をクリックします。
. 現在ログインしている *admin* ユーザーがリストに表示され、その ID が htpasswd_provider:admin 認証システムによって提供されていることがわかります。
+
image::module-02-sec-comp/24-user_list.png[title="User List", link=self, window=blank, width=100%]
+
NOTE: 以前に他の認証ソースが設定されておらず、デフォルトの kubeadminアカウントとしてログインしている場合は、最初の認証ソースの設定を支援するウィザードがここに表示されます。

ラボのこのセクションでは、インフラストラクチャを検査する監査担当者向けに、表示権限を持つ読み取り専用アカウントを作成しました。前述の通り、Red Hat OpenShiftのRBACは非常に汎用性が高く、 https://docs.redhat.com/en/documentation/openshift_container_platform/4.18/html/authentication_and_authorization/using-rbac[こちら^]のドキュメントをご覧いただくことで、その他のカスタマイズされたロールやロールバインディングについてもご確認いただけます。


== まとめ

このモジュールでは、会社の年次セキュリティ監査の準備をしました。OpenShift Compliance Operator を使用して環境をスキャンし、設定を適用してセキュリティ基準を満たしていることを確認し、RBAC を設定して特定のユーザーのみに制限付きアクセスを許可する方法を示すことで、OpenShift Virtualization インフラストラクチャのセキュリティ強化とセキュリティ強化を実現できることを実証しました。
