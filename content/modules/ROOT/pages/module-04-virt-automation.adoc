= 仮想マシンの自動化

== はじめに

「Legacy Systems Inc.」では、VMフリートの急速な拡大に伴い、パッチ適用、リソース変更、状態管理といった手作業による反復的なタスクが大幅に増加しています。VM管理者である私たちは、この増加に追随することに苦慮しており、イノベーションを起こし、ビジネスニーズに迅速に対応することが難しくなっています。組織は、既存のワークロードや関連サービスへの影響を最小限に抑えながら、既存の仮想マシンを別のプラットフォームに簡単に移行できるソリューション、そしてVMライフサイクルを自動化して効率性とデリバリー速度を向上させるソリューションを必要としています。このモジュールでは、仮想マシンの動的なインベントリを作成する方法と、Ansible Automation Platformを活用して仮想インフラストラクチャ管理タスクを自動化する方法について説明します。

== OpenShift 仮想マシンの動的インベントリの作成

目的:

動的インベントリにより、Ansible Automation Platform (AAP) は外部ソースからシステムリストを自動的に取得・更新できるため、手動管理が不要になります。

このラボでは、OpenShift Virtualization からデータを取得する動的インベントリを設定します。これにより、AAP は OCP クラスターの *vms-aap-day2* ネームスペースにある OpenShift VM を管理できるようになります。

== 自動VM管理

=== ゲストVMの 停止・起動・再起動

OpenShift コンソールの操作に慣れてきたので、管理業務を簡素化するためにどのようなアクティビティを自動化できるかを見ていきましょう。

このセクションでは、Ansible Automation Platform (AAP) を使用して、Red Hat OpenShift Virtualization で実行されているゲスト VM のライフサイクルを管理する方法を学習します。

Playbook や VM タスクファイルの作成など、基本的な作業の大部分はすでに完了していますが、このラボのセクションでは、各要素がどのように連携するか、そして AAP 経由で自動化を実行する方法を理解することに重点を置きます。

まず、特定のネームスペース内のすべての VM の停止、起動、再起動といった、VM ライフサイクルの一般的なアクションをいくつか実行します。これらのタスクは、これらのアクションの背後にある自動化がどのように構成されているかを示すために設計されています。

=== 既存の設定

お客様のエクスペリエンス向上のため、以下のコンテンツが既に作成および構成されています。

* *tasks/main.yml* ファイルには、動的なタスク追加ロジックが事前に設定されています。
* 入力変数に基づいて適切なタスクを呼び出す Ansible プレイブック (*manage_vm_playbook.yml*) が既に用意されています。
* VM の停止、起動、再起動を行うための個別のタスクファイル (*stop_vm.yml*、*start_vm.yml*、*restart_vm.yml*) が事前に作成されています。

これらのファイルを作成または変更する必要はありませんが、Ansible Automation Platform でジョブテンプレートを作成する際に参照することになるため、その動作を理解しておくことが重要です。

=== タスクファイルについて

各タスクファイルは、特定のネームスペース（この場合は *vms-aap-day2*）内のすべての仮想マシンを取得し、現在のステータスに基づいてアクション（停止、起動、再起動）を実行します。
*ansible.builtin.debug* タスクは、VM リソース *vm_info* の構造を理解するための洞察を提供し、動的な Ansible タスクの作成に必要な主要なフィールドを特定します。

=== stop_vm.yml

このタスク ファイルは、特定のネームスペース内で現在実行中のすべての VM を停止します。

[source,yaml]
----
---
- name: Get all VirtualMachines in the namespace
  redhat.openshift_virtualization.kubevirt_vm_info:
    namespace: "{{ vm_namespace }}"
  register: vm_info

- name: Debug the vm_info variable
  ansible.builtin.debug:
    var: vm_info

- name: Stop VM using OpenShift API
  ansible.builtin.uri:
    url: "{{ OCP_HOST }}/apis/subresources.kubevirt.io/v1/namespaces/{{ vm_namespace }}/virtualmachines/{{ item.metadata.name }}/stop"
    method: PUT
    headers:
      Authorization: "Bearer {{ OCP_BEARER_TOKEN }}"
    validate_certs: false
    status_code:
      - 202
  loop: "{{ vm_info.resources }}"
  loop_control:
    label: "{{ item.metadata.name }}"
  changed_when: item.status.printableStatus != "Stopped"
----

=== start_vm.yml

このタスク ファイルは、指定されたネームスペース内で現在停止されているすべての VM を起動します。

[source,yaml]
----
---
- name: Get all VirtualMachines in the namespace
  redhat.openshift_virtualization.kubevirt_vm_info:
    namespace: "{{ vm_namespace }}"
  register: vm_info

- name: Debug the vm_info variable
  ansible.builtin.debug:
    var: vm_info

- name: Start VM using OpenShift API
  ansible.builtin.uri:
    url: "{{ OCP_HOST }}/apis/subresources.kubevirt.io/v1/namespaces/{{ vm_namespace }}/virtualmachines/{{ item.metadata.name }}/start"
    method: PUT
    headers:
      Authorization: "Bearer {{ OCP_BEARER_TOKEN }}"
    validate_certs: false
    status_code:
      - 202
  loop: "{{ vm_info.resources }}"
  loop_control:
    label: "{{ item.metadata.name }}"
  changed_when: item.status.printableStatus != "Running"
----

=== restart_vm.yml

このタスク ファイルは、特定のネームスペース内で現在実行中のすべての VM を再起動します。

[source,yaml]
----
---
- name: Get all VirtualMachines in the namespace
  redhat.openshift_virtualization.kubevirt_vm_info:
    namespace: "{{ vm_namespace }}"
  register: vm_info

- name: Debug the vm_info variable
  ansible.builtin.debug:
    var: vm_info

- name: Restart VM using OpenShift API
  ansible.builtin.uri:
    url: "{{ OCP_HOST }}/apis/subresources.kubevirt.io/v1/namespaces/{{ vm_namespace }}/virtualmachines/{{ item.metadata.name }}/restart"
    method: PUT
    headers:
      Authorization: "Bearer {{ OCP_BEARER_TOKEN }}"
    validate_certs: false
    status_code:
      - 202
  loop: "{{ vm_info.resources }}"
  loop_control:
    label: "{{ item.metadata.name }}"
  changed_when: item.status.printableStatus != "Running"
----

これらのタスクファイルは、*ansible.builtin.uri* モジュールを使用して OpenShift REST API と直接やり取りし、仮想マシンの停止、起動、再起動といった適切なライフサイクルアクションを呼び出します。

さらに、デバッグタスクは、*kubevirt_vm_info* モジュールによって返される VM データの構造を視覚化するのに役立ち、以下のように分類されます。

* *kubevirt_vm_info* モジュールは、ネームスペース内のすべての VM を取得します。
* *metadata.name*: 仮想マシンの名前。
* *metadata.namespace*: VM が属するネームスペース。
* *loop_control* オプションは、タスクの各反復処理にラベルを設定し、出力に VM 名 (*item.metadata.name*) を表示します。これにより、プレイブックの出力がより読みやすくなり、デバッグが容易になります。
* *status.printableStatus*: VM の現在のステータス (例: 停止、起動、再起動)。

*ansible.builtin.debug* モジュールのスニペット サンプルを以下に示します。

[source,yaml]
----
changed: true
result:
  apiVersion: kubevirt.io/v1
  kind: VirtualMachine
  metadata:
    annotations:
      kubectl.kubernetes.io/last-applied-configuration: >
        ...
    ...
    name: rhel9-vm1
    namespace: vms-aap-day2
  spec:
    ...
  status:
    ...
    printableStatus: Stopped
  ...
----

=== ゲストVMへのパッチ適用

この演習では、Ansible Automation Platform を使用してセキュリティ関連のアップデートのみを適用することで、RHEL 仮想マシンへのパッチ適用を自動化します。

対象となる仮想マシンは、前の手順で設定した動的インベントリ（具体的には *OpenShift Virtual Machines* インベントリ）に既に含まれています。

プレイブックやタスクを一から作成するのではなく、提供されている自動化コンテンツ（以下を含む）を使用します。

* dnf モジュールを使用してセキュリティ更新を実行するタスクファイル。
* システム登録とパッチ適用を担当するロールを実行するプレイブック。

目標は、このコンテンツがどのような機能を果たすのかを理解し、Ansible Automation Platform の Web UI を使用して自動化を実行するためのジョブテンプレートを作成することです。

NOTE: このラボでは、機密性の高い認証データを安全に処理するために Vault 認証情報を使用し、RHEL システムを Red Hat に登録するためにサブスクリプション管理ロールを使用します。これにより、VM がアップデート用の適切なリポジトリにアクセスできることが保証され、安全な自動化の実践が可能になります。

=== 提供されているタスクファイルを理解する: update_security_packages.yml

このタスクファイルは、redhatone.vm_management.vm_management ロールのtasks/ディレクトリ内に保存されます。このタスクファイルは、ansible.builtin.dnfモジュールを使用して、インベントリ内のすべてのホストで最新のセキュリティ関連アップデートをスキャンし、インストールします。

[source,yaml]
----
- name: Update security-related packages on all hosts
  ansible.builtin.dnf:
    name: "*" <1>
    security: true <2>

=== CPUとメモリリソースのホットプラグ

仮想ワークロードの大きなメリットの一つは、ワークロードの需要に合わせて、ワークロードが使用するリソースをリアルタイムで調整できることです。RAMを物理的に追加したりプロセッサをアップグレードしたりするためにサーバーをシャットダウンしなければならなかった時代と比べると、追加リソースをホットプラグすることでVMリソースを動的に拡張できる機能は、大幅な時間節約につながります。また、ゲストから収集したメトリクスに基づいて、Ansible Automation Platformを使用してこれらの要求のスケールアップとスケールダウンを自動化できるため、リソース消費と物理的な管理時間の両方を効率化できます。

このセクションでは、Ansible Automation Platformとredhat.openshift_virtualizationコレクションを使用して、実行中の仮想マシン（VM）にCPUとメモリのリソースをホットプラグする方法を学習します。

ホットプラグとは、CPUやメモリなどのハードウェアリソースを、実行中のVMに再起動なしで追加または削除できる機能です。この機能は動的なワークロードにとって非常に重要であり、需要に応じてリソースを拡張しながら、ダウンタイムを最小限に抑えることができます。

この演習では、OpenShift Virtualization で再利用可能なオブジェクトである *instance types* の使用に焦点を当てます。インスタンスタイプは、VM のリソースと特性を定義します。インスタンスタイプは、VM 間で一貫した構成を可能にすることで、リソース管理を簡素化します。

==== インスタンスタイプとは何ですか?

インスタンスタイプは、新しいVMのリソース（CPUやメモリなど）と特性を定義する再利用可能な設定オブジェクトです。
OpenShift Virtualizationは、次の2種類のインスタンスタイプを提供します。

. *VirtualMachineInstancetype*: 特定のネームスペースに限定されたインスタンスタイプ用のネームスペースオブジェクト。
. *VirtualMachineClusterInstancetype*: すべてのネームスペースで利用可能なインスタンスタイプ用クラスター全体のオブジェクト。

どちらのタイプも同じVirtualMachineInstancetypeSpecを共有しているため、カスタム設定を定義したり、OpenShift Virtualizationのインストール時にデフォルトで含まれるさまざまなインスタンスタイプを使用したりできます。

インスタンスタイプを使用することで、VM構成管理を簡素化し、すべてのデプロイメント全体で一貫性を確保できるため、リソースのホットプラグには *recommended approach* となります。

このラボでは、主にインスタンスタイプの使用に焦点を当てながら、コンテキストに合わせてVM仕様を直接変更するという従来のアプローチについても学習します。

NOTE: 従来の方法は、インスタンス タイプを使用しない VM を作成する場合にのみ機能します。

==== VM がインスタンス タイプを使用しているかどうかを識別する方法

VM がインスタンス タイプを使用して作成されているかどうかを確認するには、次の手順に従います。

. OpenShift Virtualization コンソールで、*rhel9-vm1* の *Overview* タブに移動します。
. *Details* セクションで、次の項目を探します。
   - *Instance Type*: VM がインスタンス タイプを使用する場合、このフィールドには VM に適用されているインスタンス タイプの名前が表示されます (例: u1.small)。
   - *Template*: インスタンス タイプが使用されていない場合、このフィールドには「なし」または VM の作成に使用されたテンプレートの名前が表示されます。
+
image::module-04-virt-automation/26-vm_details.png[title="VM Details", link=self, window=blank, width=100%]

VMにリソースをホットプラグする場合、instance_type方式が推奨されます。これにより、OpenShift Virtualizationの強力な機能を活用しながら、複数のVM間で一貫性と再利用性を確保できます。

==== 事前に作成された hot_plug.yml ファイルを使用してリソースを更新する

hot_plug.ymlファイルは、実行中のVMに新しいインスタンスタイプを適用して更新するタスクで構成されています。このアプローチにより、VMを再作成したり電源をオフにしたりすることなく、CPUとメモリのリソースを動的に追加できます。

[source, yaml]
----
- name: Swap Instance Type to add more Resources
  redhat.openshift_virtualization.kubevirt_vm: <1>
    name: "rhel9-vm1" <2>
    namespace: "{{ vm_namespace }}" <3>
    state: present <4>
    run_strategy: RestartOnError <5>
    instancetype: <6>
      name: "{{ instance_type }}" <7>
      revisionName: "" <8>
----
<1> *redhat.openshift_virtualization.kubevirt_vm*: OpenShift Virtualization で VM を管理するために使用されるモジュールを指定します。
<2> *name*: 新しいリソースが適用される VM の名前。
<3> *namespace*: VM が存在するネームスペース。
<4> *state*: VM が存在し、利用可能であることを確認します。
<5> *run_strategy*: エラーが発生した場合に VM を再起動しますが、手動で停止したマシンは起動しません。
<6> *instancetype*: VM のインスタンスの種類を定義し、事前構成されたリソース設定またはカスタム リソース設定を使用できるようにします。
<7> *instancetype.name*: 適用するインスタンス タイプの名前。
<8> *instancetype.revisionName*: 必要に応じて、インスタンスタイプの正確なリビジョンを指定し、VMとの互換性を確保します。通常は自動生成されるため、空のままになります。

NOTE: このタスクメソッドを使用するには、インスタンスタイプを使用してVMを作成する必要があります。それ以外の場合は、クラシックメソッドを使用する必要があります。

==== クラシックメソッド: 仕様を直接変更する (情報のみ)

クラシックメソッドでは、VM のスペックファイルを直接変更して CPU とメモリのリソースを更新します。
このアプローチは柔軟性に優れていますが、インスタンスタイプが提供する再利用性と一貫性が欠けているため、複数の VM にまたがるリソースの管理には適していません。

[source, yaml]
----
- name: Modify CPU & Memory Resources
  redhat.openshift_virtualization.kubevirt_vm: <1>
    name: "rhel9-vm2" <2>
    namespace: "{{ vm_namespace }}" <3>
    state: present <4>
    spec: <5>
      domain: <6>
        cpu: <7>
          sockets: 2
        memory: <8>
          guest: 4Gi
----
<1> *redhat.openshift_virtualization.kubevirt_vm*: OpenShift Virtualization で VM を管理するために使用されるモジュールを指定します。
<2> *name*: 変更する VM の名前。
<3> *namespace*: VM が存在するネームスペース。
<4> *state*: VM が目的の状態 (この場合は存在) にあることを確認します。
<5> *spec*: VM の仕様を直接変更します。
<6> *spec.domain*: VM の仮想化環境に関連する設定が含まれます。
<7> *spec.domain.cpu*: VM の CPU ソケットの数を指定します (例: 2)。
<8> *spec.domain.memory*: VM に割り当てられるメモリを定義します (例: 4Gi)。

NOTE: クラシック VM はこのラボ演習の一部ではありません。クラシック メソッドは情報提供のみを目的としています。

=== 仮想マシンのバックアップと復元

仮想マシン管理において最も重要な側面の一つは、信頼性の高いバックアップとリストア機能によって事業継続性を確保することです。稼働中の仮想マシンのポイントインタイムスナップショットを取得し、災害、システム障害、または意図しない変更が発生した場合に迅速にリストアする機能は、従来のバックアップ方法と比較して、組織の時間とリソースを大幅に節約できます。

この演習では、Ansible Automation Platform の VM スナップショットを使用して、仮想マシンのバックアップとリストアを自動化します。この機能により、運用効率を維持しながら、仮想化されたワークロードを大規模に保護できます。

OpenShift Virtualization の仮想マシンスナップショットは、接続されたすべての Container Storage Interface (CSI) ボリュームと VM 構成メタデータを含む、特定の時点における VM の完全な状態とデータをキャプチャします。稼働中の VM の場合、QEMU ゲストエージェントはスナップショット作成中の I/O 操作を調整し、ファイルシステムをフリーズ、スナップショットを取得、そしてファイルシステムをアンロードすることでデータの整合性を確保します。

スナップショットは、以下の 3 つの OpenShift API を通じて管理されます。

* *VirtualMachineSnapshot*: スナップショットを作成するためのユーザー要求を表し、VMの現在の状態に関する情報が含まれています。
* *VirtualMachineSnapshotContent*: VMスナップショットコントローラによって作成されたクラスタ上のプロビジョニングされたリソース（実際のスナップショット）を表します
* *VirtualMachineRestore*: スナップショットからVMを復元するというユーザーリクエストを表します

=== 既存の設定

お客様のエクスペリエンスを向上させるために、次のコンテンツがすでに作成され、構成されています。

* スナップショット自動化タスク (*snapshot_vms.yml* および *_snapshot_vm.yml*) は、ループベースのアプローチを使用して VM スナップショットを処理するように事前に作成されています。
* 復元自動化タスク (*restore_vm_snapshots.yml* および *_restore_vm_snapshot.yml*) は、VM の停止、復元、再起動を含む復元ワークフロー全体を管理するために事前に作成されています。
* *manage_vm_playbook.yml* プレイブックは、VM のスナップショットを取得するか復元するかを指定する入力変数に基づいてこれらのタスクを実行するように既に構成されています。

これらのファイルを作成したり変更したりする必要はありませんが、Ansible Automation Platform でジョブ テンプレートを作成するときに参照することになるため、その動作を理解しておくことが重要です。

=== 提供されているスナップショットタスクファイルについて

スナップショット自動化では 2 層のアプローチが使用され、1 つのタスク ファイルがループを使用して複数のスナップショットを処理し、インクルード タスク ファイルが個々の VM スナップショットを取得します。

=== snapshot_vms.yml

このメイン タスク ファイルは、コンマで区切られた VM 名の文字列を処理し、Ansible のループ機能を使用して各 VM に対して個別のスナップショット タスクを作成します。

[source,yaml]
----
---
- name: Snapshot individual VM
  ansible.builtin.include_tasks:
    file: _snapshot_vm.yml
  loop_control:
    loop_var: vm_to_snapshot
  loop: "{{ vms_to_snapshot.replace(' ','').split(',') }}"
  when: vms_to_snapshot | default('', True) | length > 0
----

**タスクの説明:**

* *when*: フィルターを使用して変数の状態をチェックする前に、`vms_to_snapshot` 変数にコンテンツが含まれているかどうかを検証します。
* *loop*: カンマ区切りのVM名を処理し、スペースを削除し、Jinja2関数を使用してリストを作成します。
* *loop_control/loop_var*: ループの各反復ごとに変数名（`vm_to_snapshot`）を設定します
* *ansible.builtin.include_tasks*: スナップショット プロセスを完了するために必要な手順 (タスク) をキャプチャする各 VM に含まれるタスク ファイル `_snapshot_vm.yml` を呼び出します。

=== _snapshot_vm.yml

アンダースコア "_" で始まるタスクファイルは、別のタスクファイルに含まれていることを示します。このファイルは、OpenShift APIを使用して単一のVMのスナップショット作成を実際に処理し、スナップショットのコアロジックを含んでいます。

[source,yaml]
----
---
- name: Verify VM to Snapshot Provided
  ansible.builtin.assert:
    that:
      - vm_to_snapshot | default('', True) | length > 0
    quiet: True
    fail_msg: VM to Snapshot not specified

- name: Get VirtualMachine to snapshot
  redhat.openshift_virtualization.kubevirt_vm_info:
    namespace: "{{ vm_namespace }}"
    name: "{{ vm_to_snapshot }}"
  register: vm_info

- name: Create Snapshot
  redhat.openshift.k8s:
    state: present
    definition:
      apiVersion: snapshot.kubevirt.io/v1alpha1
      kind: VirtualMachineSnapshot
      metadata:
        generateName: "{{ vm_info.resources[0].metadata.name }}-"
        namespace: "{{ vm_info.resources[0].metadata.namespace }}"
        ownerReferences:
          - apiVersion: kubevirt.io/v1
            blockOwnerDeletion: false
            kind: VirtualMachine
            name: "{{ vm_info.resources[0].metadata.name }}"
            uid: "{{ vm_info.resources[0].metadata.uid }}"
      spec:
        source:
          apiGroup: kubevirt.io
          kind: VirtualMachine
          name: "{{ vm_info.resources[0].metadata.name }}"
    wait: true
    wait_condition:
      type: Ready
  when: "'resources' in vm_info and vm_info.resources | length == 1"
----

**タスクの説明:**

このタスクファイルには、以下の3つのタスクが含まれています。

. `ansible.builtin.assert` を使用して、`vm_to_snapshot` という変数が指定されていることを確認します。
. `kubevirt_vm_info` を使用して、`VirtualMachine` リソースの定義を取得し、`vm_info` に保存します。
. `redhat.openshift.k8s` モジュールを使用して、新しい `VirtualMachineSnapshot` リソースを作成します。

スナップショット作成の主な詳細：

* *generateName*: OpenShift は、`name` が指定されていない場合に一意の名前を生成する機能を備えています。
* *ownerReferences*: `VirtualMachineSnapshot` と `VirtualMachine` の関係を作成し、VM が削除された場合に OpenShift ガベージ コレクターが自動的にスナップショットを削除するようにします。
* *wait/wait_condition*: スナップショットが正常に完了するまで実行を一時停止します（条件タイプ `Ready` が `true` に設定されます）
* *when*: VMリソースが1つだけ見つかった場合にのみスナップショットが作成されるようにする

=== 提供されている復元タスクファイルについて

復元自動化機能は、VMの停止、スナップショットからの復元、そしてVMの再起動というワークフロー全体を処理します。スナップショットの作成とは異なり、スナップショットからの復元を開始する前に、VMの電源をオフにする必要があります。この自動化は、スナップショットプロセスと同じ2層構造のパターンに従います。

=== restore_vm_snapshots.yml

このメインタスクファイルは、コンマ区切りのスナップショット名文字列を処理し、個別の復元タスクを作成します。スナップショットタスクとの主な違いは、VM名ではなくスナップショット名を参照することです。

[source,yaml]
----
---
- name: Restore VM Snapshot
  ansible.builtin.include_tasks:
    file: _restore_vm_snapshot.yml
  loop_control:
    loop_var: vm_snapshot
  loop: "{{ vm_snapshots.replace(' ','').split(',') }}"
  when: vm_snapshots | default('', True) | length > 0
----

このタスクは、復元する `VirtualMachineSnapshot` リソース名のコンマ区切り文字列を含む `vm_snapshots` という変数を操作します。

=== _restore_vm_snapshot.yml

このタスクファイルは、以下の手順に従って、完全な復元ワークフローを管理します。

. 指定されたスナップショット名に基づいて `VirtualMachineSnapshot` を取得します。
. 仮想マシンを停止します。
.  `VirtualMachineRestore` リソースを作成し、復元が完了するまで待機します。
. 仮想マシンを起動します。

[source,yaml]
----
---
- name: Verify VM Snapshot Provided
  ansible.builtin.assert:
    that:
      - vm_snapshot | default('', True) | length > 0
    quiet: True
    fail_msg: VM Snapshot not specified

- name: Get VirtualMachine Snapshot
  kubernetes.core.k8s_info:
    api_version: snapshot.kubevirt.io/v1alpha1
    kind: VirtualMachineSnapshot
    namespace: "{{ vm_namespace }}"
    name: "{{ vm_snapshot }}"
  register: vm_snapshot_instance

- name: Create Restore
  block:
    - name: Stop Virtual Machine
      redhat.openshift_virtualization.kubevirt_vm:
        name: "{{ vm_snapshot_instance.resources[0].metadata.ownerReferences[0].name }}"
        namespace: "{{ vm_snapshot_instance.resources[0].metadata.namespace }}"
        run_strategy: Halted
        wait: true

    - name: Create Restore
      redhat.openshift.k8s:
        state: present
        definition:
          apiVersion: snapshot.kubevirt.io/v1alpha1
          kind: VirtualMachineRestore
          metadata:
            generateName: "{{ vm_snapshot_instance.resources[0].metadata.ownerReferences[0].name }}-"
            namespace: "{{ vm_snapshot_instance.resources[0].metadata.namespace }}"
            ownerReferences:
              - apiVersion: kubevirt.io/v1
                blockOwnerDeletion: false
                kind: VirtualMachine
                name: "{{ vm_snapshot_instance.resources[0].metadata.ownerReferences[0].name }}"
                uid: "{{ vm_snapshot_instance.resources[0].metadata.ownerReferences[0].uid }}"
          spec:
            target:
              apiGroup: kubevirt.io
              kind: VirtualMachine
              name: "{{ vm_snapshot_instance.resources[0].metadata.ownerReferences[0].name }}"
            virtualMachineSnapshotName: "{{ vm_snapshot_instance.resources[0].metadata.name }}"
        wait: true
        wait_timeout: 600
        wait_condition:
          type: Ready

    - name: Start Virtual Machine
      redhat.openshift_virtualization.kubevirt_vm:
        name: "{{ vm_snapshot_instance.resources[0].metadata.ownerReferences[0].name }}"
        namespace: "{{ vm_snapshot_instance.resources[0].metadata.namespace }}"
        run_strategy: Always
        wait: true
  when: "'resources' in vm_snapshot_instance and vm_snapshot_instance.resources | length == 1"
----

**タスクの説明:**

* *kubernetes.core.k8s_info*: スナップショットの詳細を取得して、関連付けられている VM を識別します (仮想マシンに固有の `kubevirt_vm_info` の代わりに、これにより任意の OpenShift リソースを取得できます)
* *block*: 最後に条件チェックを行って復元手順をグループ化します
* *Stop Virtual Machine*: `run_strategy: Halted` を使用して復元を開始する前に VM の電源をオフにします
* *Create Restore*: 復元にはデフォルトの 120 秒よりも長くかかる可能性があるため、600 秒 (10 分) の `wait_timeout` で VirtualMachineRestore リソースを作成します。
* *Start Virtual Machine*: `run_strategy: Always` を使用して復元が完了したら、VM の電源を再びオンにします。
